5.1 Learning goals

By the end of this session you should be able to:

  • explain why exact dynamic programming does not scale to searching a whole database;
  • describe BLAST’s seed-extend-evaluate heuristic, and how MMseqs2 scales the same ideas;
  • interpret the E-value and bit score of a real BLAST result;
  • construct a small position-specific scoring matrix (PSSM) by hand, and explain why pseudocounts matter;
  • describe PSI-BLAST as BLAST iterated with a PSSM instead of a single sequence, and explain why iteration can drift;
  • explain, at a conceptual level, what a profile Hidden Markov Model adds beyond a PSSM.

5.2 The scaling problem, and BLAST’s heuristic answer

Session 4’s dynamic programming finds the provably optimal alignment between two sequences, but its cost is proportional to the product of their lengths. For two sequences a few hundred residues long, this is no problem. For searching one query against a database, it is. GenBank and UniProt hold well over a hundred million sequences between them, and running full dynamic programming against every entry would take far too long to be useful. A database search therefore needs a faster method.

BLAST (Basic Local Alignment Search Tool) is such a method, and it trades the guarantee of optimality for speed. Instead of filling a DP matrix for every database sequence, it first looks for short exact or near-exact matches. Only the promising regions that these matches point to get the expensive alignment step. Concretely, BLAST runs in three stages:

  1. Seeding. Break the query into short “words”, list every word that scores well against each of them, and scan the database for occurrences of those words.
  2. Extension. Grow each seed hit outwards, in both directions, into a full local alignment.
  3. Evaluation. Ask whether the score of the resulting alignment is better than what pure chance would produce.

Each stage is covered in its own section below. This three-stage picture is the core idea, and it is deliberately simplified. Production BLAST adds refinements such as the two-hit rule (only extend when two seeds lie close together on the same diagonal), masking of low-complexity regions, gapped extension, and corrections for unusual amino-acid composition. None of these refinements changes the logic of seed, extend, evaluate.

5.3 Stage 1: seeding — turning the query into fast lookups

The first stage turns the query into a set of short words. For protein sequences, a “word” is usually only 3 residues long, so a query of length 200 has 198 overlapping 3-letter words. BLAST does not search the database only for exact matches to these words, because a biologically real match may substitute a residue or two without losing significance. Instead, it uses a substitution matrix (BLOSUM62, from Session 4) to precompute every 3-letter combination that scores above a threshold \(T\) against each query word.

These query words and their high-scoring neighbours go into a lookup table, which is built once per query and records, for every 3-letter word, which query positions it would seed. BLAST then scans each database sequence once, from start to end. For every 3-letter word it reads, it asks the table “does this word seed anything in the query, and where?” Because that check is a single table lookup, the scan is fast and linear in the size of the database. Only the few places that produce a seed go on to the expensive extension step.

5.4 Stage 2: extension — growing a seed into a real alignment

A seed hit is only a 3-letter coincidence and not yet evidence of anything. BLAST therefore extends it outwards in both directions and recomputes a running score as it goes. The scoring uses the same substitution-matrix logic as Session 4’s dynamic programming, but without filling a full matrix. Instead, extension stops as soon as the running score has fallen too far below its own best point so far.

The X-drop rule. BLAST tracks the running score as the alignment extends, and separately the best score seen so far. If the running score ever falls more than a threshold \(X\) below that best score, the alignment is very unlikely to recover, so extension stops. The reported alignment is then trimmed back to the point where the best score occurred.

Worked example, adapted from Korf, Yandell & Bedell (2003). We treat two short strings as if they were sequences, score \(+1\) for a matching character and \(-1\) for a mismatch (ignoring spaces), and use \(X=5\):

query:    Thequickbrownfoxjumps...
database: Thequietbrownncatpurrs...

The running score climbs steadily through Thequ, dips slightly at the ick/iet mismatch, and then recovers and climbs further through brown to a peak of 9 right after ...brown/...brown. After that it falls steadily, as foxjump diverges from catpurr. Once the running score has dropped 5 points below the peak of 9, extension stops. The reported alignment is trimmed back to the peak itself, so it pairs Thequickbrown with Thequietbrown and leaves out the lower-scoring tail beyond it. The notebook reproduces this computation in code.

5.5 Stage 3: is this hit significant? E-values and bit scores

Extending every seed produces a raw alignment score. A raw score alone, however, does not say whether the alignment is meaningful or simply what we would expect from two random sequences of that length. To decide, we need to know how scores are distributed by chance. Karlin and Altschul proved in 1990 that the scores from aligning a query against random sequence data follow an extreme value (Gumbel) distribution, not a normal distribution, and this result underpins BLAST’s statistics.

From that distribution follows the expected number of alignments that score at least \(S\) purely by chance, the E-value:

\[ E = K m n\, e^{-\lambda S} \]

Here \(m\) and \(n\) are the lengths of the query and the database, and \(K\) and \(\lambda\) are constants of the particular scoring system (substitution matrix and gap penalties), which real BLAST output reports as “Karlin-Altschul statistics”. This is the simplified textbook form. Real BLAST replaces \(m\) and \(n\) by slightly smaller effective lengths (an alignment cannot start right at the end of a sequence) and adjusts for composition, but the behaviour is the same.

Two consequences of the formula matter. First, a higher score gives an exponentially smaller \(E\). Second, a bigger database (\(n\)) inflates \(E\) for the same alignment, because chance has more opportunities to produce a false hit. An E-value is therefore only meaningful together with the database it was computed against, and the same alignment can be “significant” against a small database but not against all of GenBank.

Raw scores and E-values both depend on the scoring system, which makes them awkward to compare across different searches. The bit score solves this by normalising away the scoring system:

\[ S' = \frac{\lambda S - \ln K}{\ln 2} \]

Bit scores from completely different searches, even ones that use different substitution matrices, can therefore be compared directly. A bit score is not a significance test on its own, though. There is no universal bit-score cutoff, because whether a given score is surprising still depends on the size of the search space it was found in. For significance, read the E-value.

Reading real output. A real local BLASTP search of HBB (beta-globin, P68871) against its five closest human globin relatives gives the following hits:

The first four are all confident, high-quality hits, with high percent identity, astronomically small E-values and comfortably high bit scores. Myoglobin is the interesting case. It shares the globin fold and a real evolutionary origin with haemoglobin, yet BLAST reports only a weak alignment with an E-value of 63, which taken at face value is no statistical evidence at all. That number, however, only evaluates the alignment BLAST found. If we run the same search with the two-hit rule switched off (so that every single seed gets extended; -window_size 0 in BLAST+), BLAST finds a full-length alignment, 145 residues at 25.5% identity, with an E-value of 5×10⁻¹¹. With the default settings, no pair of seeds happened to fall close enough together on the right diagonal, so the good alignment was never extended. This is the price of a heuristic. BLAST is fast because it skips most of the search, and occasionally it skips the answer, which an optimal Smith–Waterman search would not have missed.

Database size still matters as well. These E-values are relative to a tiny five-sequence database. Against a database the size of UniProtKB (about \(9\times10^{10}\) residues), the same full-length myoglobin alignment would get an E-value of about 0.007, which is significant, but only just. Relatives that have diverged further than myoglobin, such as the bacterial truncated haemoglobins, give no detectable pairwise signal at all, even with the optimal alignment (Session 6 shows that they still share the globin fold).

5.6 BLAST’s ideas at modern database scale: MMseqs2

BLAST was designed in 1990, when the protein databases held tens of thousands of sequences. Today’s metagenomic collections hold billions, and at that scale even BLAST becomes too slow. MMseqs2 (Steinegger & Söding, 2017) is a widely used modern search tool that keeps BLAST’s logic but turns one part of it around. In simplified form, it works as follows:

  1. Index the target database by short words (k-mers, typically 6–7 residues for proteins). The index is a table that maps each k-mer to the database sequences and positions where it occurs, and it is built once and reused.
  2. For each k-mer in the query, generate the similar k-mers (scored with a substitution matrix, exactly like BLAST’s neighbour words) and look them up in the index.
  3. Keep only database sequences in which two matching k-mers fall on the same diagonal, that is, at the same offset between query and target position, just as in a dot plot from Session 4. Two consistent hits are much stronger evidence of a real alignment than one.
  4. Score the surviving candidates quickly with an ungapped alignment along that diagonal, and discard the weak ones.
  5. Run the expensive gapped Smith–Waterman alignment, heavily optimised to use the processor’s vector instructions, only on the small set that is left.

The difference from classic BLAST lies in which side gets indexed. BLAST builds a lookup table from the query and its neighbour words, and then reads through every database sequence. MMseqs2 instead indexes the database once, so each query only has to look up its own k-mers. Steps 3–5 form a cascade of ever more expensive filters, each of which passes on only a small fraction of the candidates. As a result, MMseqs2 is often hundreds of times faster than BLAST at similar sensitivity. No machine learning is involved, because MMseqs2 simply engineers the same seed-extend-evaluate ideas for scale.

Like PSI-BLAST below, MMseqs2 can also iterate, turning its hits into a profile and searching again, and ColabFold uses it to build the alignments that AlphaFold needs (Session 12). Session 6 meets its structural counterpart, Foldseek, from the same group.

5.7 From one sequence to many: PSI-BLAST and the PSSM

Myoglobin sits near the edge of what a single sequence can detect, and more distant relatives lie beyond it. The reason is that ordinary BLAST scores everything against one fixed substitution matrix, whatever family the query belongs to, so a faint but real family signal is easily lost against the background of a large database. PSI-BLAST (Position-Specific Iterated BLAST) does better, because it builds a query-specific scoring matrix and refines it over several rounds:

  1. Run an ordinary BLAST search with the query sequence.
  2. Take the hits that pass the inclusion threshold (an E-value cutoff, by default stricter than the one used for reporting hits), align them to the query, and turn that alignment into a position-specific scoring matrix (PSSM), described below. Hits that are displayed but fall short of the inclusion threshold do not enter the profile.
  3. Search the database again, this time scoring with the PSSM instead of a generic substitution matrix.
  4. Repeat, so that each round’s included hits refine the PSSM further, until no new sequences pass the threshold (convergence) or a set number of rounds is reached.

This makes PSI-BLAST more sensitive than a single BLAST pass, particularly for remote homologs whose similarity to the original query is too faint for a fixed substitution matrix to catch.

Iteration is not automatically better: profile drift. Suppose that one unrelated sequence passes the inclusion threshold. It then enters the alignment and shifts the next PSSM a little towards itself. The next round finds more sequences like the intruder, which shift the profile further. After a few rounds, the “family” can be dominated by proteins that have nothing to do with the original query, often through a shared low-complexity or coiled-coil region rather than real homology. This is a general lesson that returns in the machine-learning half of the course. A model is only as good as the examples it was built from, and a model that chooses its own training data can reinforce its own mistakes. In practice, keep the inclusion threshold strict, look at what entered in each round, and check surprising late-round hits independently.

5.7.1 Building a PSSM, step by step

Session 4 ended with alignment columns, their entropy, and sequence logos. A logo describes an alignment column, whereas a PSSM turns the same column statistics into numbers that can score a new sequence. The recipe below is a teaching model. The real PSI-BLAST computation also weights the sequences and uses more sophisticated pseudocounts, as noted along the way, but every step serves the same purpose in the real thing.

1. Count. From a multiple sequence alignment, count how often each residue appears at each position. Take this small toy alignment of 5 sequences:

Position:   1 2 3 4 5
Protein 1:  A G L S P
Protein 2:  A G L T P
Protein 3:  R G I S P
Protein 4:  A A L S Q
Protein 5:  A A L S P

At position 1, 4 of the 5 sequences have A and 1 has R. At position 5, 4 have P and 1 has Q, and so on.

Real alignments are rarely this balanced. If a search returns fifty nearly identical mammalian sequences and three distant ones, raw counts would make the profile describe mammals rather than the family. Real tools therefore reduce redundancy or weight sequences, removing or down-weighting near-duplicates so that an over-represented subfamily does not dominate the counts. The exact recipe varies between programs, but the principle is what matters.

2. Add pseudocounts. Turning raw counts straight into frequencies causes two problems. First, a residue that never appears at a position gets a frequency of exactly zero, and its log-odds score becomes \(-\infty\). Second, with only 5 sequences, the absence of a residue might be bad luck rather than a real biological signal. Pseudocounts, small constants added to every count before the frequencies are computed, solve both problems. In our teaching model we add \(+1\) uniformly to the count of every residue type at every position. Conceptually, a pseudocount is a prior, that is, what we assume about a column before looking at the alignment (here, “every residue is possible”). With only five sequences the prior has a large influence, while with hundreds of sequences the observed counts swamp it. Real tools use smarter priors, for example by giving larger pseudocounts to residues that substitute easily for the observed ones (according to a substitution matrix).

3. Compare to background. Compute each residue’s background frequency \(q_j\), that is, how often it occurs in proteins generally (e.g. alanine ≈7.4%, tryptophan ≈1.3%), independently of this alignment.

4. Compute log-odds scores. For each position \(i\) and residue \(j\),

\[ S_{i,j} = \log_2 \frac{f_{i,j}}{q_j} \]

Here \(f_{i,j}\) is the (pseudocount-adjusted) observed frequency. With base 2, a score of \(+1\) means “twice as likely here as by chance”, \(+3\) means “8× as likely”, and so on. Arranged into a matrix, with one row per alignment position and one column per residue, the scores \(S_{i,j}\) are the PSSM. (Some tools store the matrix the other way round, but the orientation is only a storage convention.) Scoring a candidate sequence against the PSSM means looking up one value per position and summing them. This is the weighted-sum, or dot-product, idea from Session 1, generalised to sequence positions.

The notebook builds this PSSM from the alignment above and confirms that the highest-scoring sequence the matrix can produce is AGLSP, the alignment’s own consensus, as it should be.

Why pseudocounts really matter. With only five sequences, every frequency is a small-sample estimate, and the raw log-odds score takes it at face value. Take a position where 4 of 5 sequences show alanine (background 7.4%) and 1 shows the much rarer tryptophan (1.3%). The raw scores are \(\log_2(0.8/0.074) \approx 3.43\) for alanine and \(\log_2(0.2/0.013) \approx 3.94\) for tryptophan, so a single observation outscores four. Yet one tryptophan in five sequences could easily be chance, and the score treats it as a reliable frequency of 20%. With \(+1\) pseudocounts the frequencies become 5/25 and 2/25, and the scores fall to 1.43 and 2.62. The pseudocounts make every score more cautious, but they do not change the ranking: tryptophan still wins. A pseudocount cannot tell a lucky single observation from a real one; only more sequences can.

Gaps. A PSSM contains only substitution scores, one row per position. To align a new sequence to it, PSI-BLAST therefore uses ordinary gapped alignment, the same dynamic programming as in Session 4, with the PSSM row for position \(i\) taking the place of the substitution-matrix row for query residue \(i\). The gap-open and gap-extension penalties are the ordinary ones, the same at every position.

A PSSM is already a linear model. For an ungapped sequence \(x = x_1 x_2 \dots x_L\), the PSSM score is

\[ S(x) = \sum_{i=1}^{L} w[i, x_i], \]

where \(w[i, x_i]\) is the matrix entry for residue \(x_i\) at position \(i\). The score is thus one weight looked up per position and added up. Session 7 keeps this weighted-sum idea but learns the weights from labelled examples instead of deriving them from alignment counts.

5.8 Profile Hidden Markov Models: what a PSSM still can’t represent

A PSSM gives position-specific substitution scores, but the alignment algorithm handles gaps separately, with the same penalties everywhere. Real families are not like that. A loop between two helices may tolerate insertions of any length, while the core of the domain almost never has one. A profile Hidden Markov Model (profile HMM) therefore integrates position-specific match, insertion and deletion behaviour into one probabilistic model of the family. It uses three kinds of states, arranged in a repeating unit with one unit per alignment position:

  • Match (M) states represent a conserved position. Each has its own per-residue emission probabilities and plays the same role as one column of a PSSM.
  • Insert (I) states represent extra residues between conserved positions. The model can emit a residue from them and then loop back to allow more than one.
  • Delete (D) states represent a skipped conserved position and emit nothing at all.

Special Begin and End states bookend the model. Transitions connect the M/I/D states of consecutive positions (e.g. \(M_i \to M_{i+1}\), \(M_i \to I_i\), \(M_i \to D_{i+1}\)), and each transition has its own learned probability.

Why “hidden”. For an observed residue in a real sequence, the model never tells you directly whether it came from a Match state or an Insert state. That has to be inferred from the path through the states that best explains the whole sequence, using the emission and transition probabilities together. The states generate what you observe, but they themselves stay hidden.

This is the extra structure that PSSMs lack, and it is why profile HMMs, not PSSMs, are the standard tool behind large-scale protein family databases such as Pfam. A profile HMM trained on a protein family can recognise a new sequence as a member even when it has a genuinely different number of residues in a variable region. The model itself has learned where insertions and deletions are common in that family, which a PSSM with uniform gap penalties can only approximate.

NoteWhat neither a PSSM nor a profile HMM can represent

Both models score a sequence position by position. The score is a sum over columns, so each position contributes independently of the others. Real proteins do not always work that way. When mutations interact, so that the effect of one depends on the residue at another position (epistasis), no profile can capture it. Session 9 shows a protein where this matters (all 160,000 variants at four positions of GB1), and Session 12 shows how pairwise models fitted to an alignment (direct coupling analysis) add those interactions.

5.9 Worked example: a real profile-HMM hit on HBB

The same idea works on a real sequence at production scale. To tie this back to the HBB (beta-globin) locus from Session 3, we search Pfam’s library of profile HMMs against the real UniProt entry P68871 (HBB_HUMAN), fetched live via EBI’s InterPro API. The search finds a match to PF00042 (“Globin”), spanning residues 27-142 of the 147-residue protein, with an E-value of around \(1.3\times10^{-29}\). In a database of this size, essentially no match that good is expected by chance. The profile HMM thus does on a real sequence what the toy PSSM above did on paper: it scores how well a sequence matches a family, position by position.

The same pattern (submit a job, wait for it, fetch the result) works for most large bioinformatics services, and it is how you will usually run big searches from your own code.
